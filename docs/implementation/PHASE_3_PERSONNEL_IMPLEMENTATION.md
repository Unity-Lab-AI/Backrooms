## Player behavior

Personnel lists actual employed pawns and native food/rest/joy/mood, bed ownership and availability. Inspect shows native traits, health conditions, skills/passions, disabled-work reasons, initialized priorities, current schedule and real apparel/equipment/inventory. Missing needs are not fabricated. Company role selection changes only the saved role; it neither sets native work priorities nor resets skills, needs, ideology or schedules. Existing native Work/Assign/Health controls remain available.

Request applicants is explicit and requires a supported branch and loaded HQ. Its saved cooldown cannot be bypassed by closing the tab. Up to three queued records are created; each game tick processes at most one native generation call. The request uses the real constructor, factionless NonPlayer context, explicit adult stage, forced-new identity, no generated pawn relations, no generated food or weapons and native ordinary apparel. Candidates keep native traits/health/skills rather than being altered to meet a role. Native generation's own retry limit still applies; failure is retained, not rerolled every tick. The policy is data, not a new ThingDef or PawnKind.

Offer terms are saved before acceptance. The quote shows onboarding separately from the daily wage and explains the next existing company payroll cutoff. Hiring preflights a clear, unfogged, native colony-reachable edge cell before charging. The same held pawn is spawned, recruited through Core `RecruitUtility.Recruit`, and added to the existing staff list once. Their real generated apparel/inventory moves with that pawn. No money becomes silver, no duplicate payroll counter is introduced and no map, equipment or employee is fabricated by an inspection screen.

`NextPayrollTick` projects the first scheduled cutoff strictly after the current game tick without changing the saved billing cursor. It uses 64-bit arithmetic and returns `-1` with explicit UI text when the next cutoff reaches or exceeds the company's `int.MaxValue` stopped-at-tick-limit sentinel. This prevents an overdue catch-up cursor appearing as the candidate's first wage date. The lead's corresponding company wage filter includes a person only for a cutoff strictly after their actual `hiredTick`, preventing retrospective charges for days before registration. The offer does not promise prorated wages or a separate payroll clock.

The latest owner content restriction is respected: **no new item/equipment/furniture/bench/PawnKind assets or content** are created. This increment uses native Core people and goods, original C# logic, policy Defs and UI text only. It does not depend on any optional DLC/mod.

## State and recovery

- Personnel schema **1** is independent of current campaign schema **2**. An old save gets an empty component without offers, grants, charges or new employees; no campaign migration is required for this increment. Unknown or inconsistent personnel schema disables its actions and preserves held data with a keep-original-save warning.
- IDs use saved monotonic branch applicant sequences, then fixed hire/onboarding/refund/staff suffixes. Quotes come from the saved offer, never a UI-supplied amount. Company transaction receipts are reconciled before retry/refund; mismatched receipts refuse.
- One `ThingOwner<Pawn>` deep-owns unspawned candidates. Offer records reference the same pawn. They are not automatically ticked as off-site staff and do no work. On arrival, normal native pawn simulation operates. This bounded board does not simulate off-screen applicant living arrangements.
- The journal is written before native calls. `GenSpawn` removes the holder before SpawnSetup, so exceptions inspect actual spawned/held/world state. A detached original is returned to the same holder; an already spawned person stays where they are. A retry cannot create another pawn or move an arrived person back to the edge.
- Native recruitment may change pawn kind, work settings and population records. The company role is a separate saved field. If an interrupted call already produced a player pawn, retry does not repeat SetFaction or its priority/population side effects; it requires the resulting native player/work/needs state before registration. Missing native state remains a visible recovery refusal requiring the native/mod error to be resolved; the service does not invent a replacement.
- Cancel/refund requires the same living original pawn in our off-site holder, no employee record, no observed arrival and no recruitment. A failed spawn is eligible only after a saved reconciliation confirms off-site custody. Actual/ambiguous arrival cannot be refunded. Refund uses a separate exact receipt; retry after refund cannot reactivate hiring.
- Decline/expiry/cancel passes the same unspawned pawn to `WorldPawns` once using native Decide behavior. A failure retains the release journal and offers Retry release. Native world ownership/GC then owns that person; terminal history keeps identity/name without a second deep reference. Reentrant public mutations are refused during generation/hire/release.
- Keep **64 safely terminal summaries**, plus every open/recovery/ambiguous record. `Unavailable` is open and blocks a new applicant request until resolved. Its explicit dismiss action requires a matching branch/schema, no charge/refund or arrival/recruitment/staff receipt, and the original pawn to be positively known as spawned, world-owned, held by another holder, destroyed or discarded. It only drops this component's reference, preserving the applicant name, load ID and custody-change reason; it never releases, de-spawns, transfers or changes the external pawn. A detached pawn with no known owner remains attached to its record, and the offer stays open. Dismissed summaries use a new appended status value, then participate in the 64-record terminal compaction. Compaction deletes only terminal record summaries, never pawns, employee records or ledger receipts. Saved sequence and compacted-count values persist; a pruned offer ID refuses rather than recreating a hire. Active/recovery custody is never pruned. Recent UI history displays 12 entries.
