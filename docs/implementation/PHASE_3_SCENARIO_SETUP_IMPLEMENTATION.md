## Implemented source and player route

1. New company starts use native `ScenPart_ConfigPage_ConfigureStartingPawns`, five selected candidates by default and ten initial choices, with the native player colony's `Colonist` kind. The old five custom PawnKindDefs and old page class remain readable for existing development saves, but new starts do not select them.
2. The native pawn page is followed by `Page_RimroomsCompanySetup` supplied by the company part's `GetConfigPages()`. The page rereads the actual selected pawn instances. It displays the accepted count, chosen tile, funding/wages, carried/equipped/worn gear, additional native possessions, native supply summaries and a separate fixed-facility manifest. The latter includes building counts, structure/conduit counts and initial fuel/battery fractions.
3. Roles are assigned by actual pawn reference. The five role definitions supply initial suggestions, disabled-work/capacity/violence warnings and advisory skill targets. They do not change pawn kinds, skills, traits, health, relationships or possessions. The former Rimrooms work-priority overwrite is removed. Native `PrepForMapGen` still assigns native initial work priorities; this does not promise retention of an optional mod's separate priority system.
4. The page rejects an invalid roster outside 1–20, duplicates, dead/destroyed/nonhumanlike selected people, missing tile or invalid start definition before map generation. It does not silently trim selected people. Native optional candidates remain the native game's responsibility. Back/reopen or changed roster/role resets acknowledgment; continuing requires the final review.
5. Fourteen default loose supply lines now exist as native `ScenPart_StartingThing_Defined` parts. The headquarters builder no longer creates `start.stock`. Native/EdB changes to those parts therefore feed the same arrival. Native starting possessions are allowed and displayed; this deliberately differs from the earlier no-possessions start. The fixed facility is not multiplied for larger rosters. It remains five ordinary beds plus medical beds and needs player expansion. Existing legacy gate/field equipment references remain pending the separate provider migration; no new ThingDef is introduced here.
6. A guarded subclass of native `ScenPart_PlayerPawnsArriveMethod` performs the standing arrival. Its saved started receipt is set before native creation/placement. It records observed newly spawned load IDs, definitions and counts even when that call throws, un-forbids newly arrived items, and verifies the actual selected staff arrived on the headquarters map. It never retries the native object factories automatically.

## Saved owners and existing saves

| Owner | Saved fields and behavior |
| --- | --- |
| `RimroomsStartupComponent`, schema 1 | Start Def, acknowledgment, chosen `PlanetTile`, actual pawn references, stable pawn load IDs, role IDs and accepted supply-summary text. Native systems retain pawn/item custody. No generation or grants occur in construction, loading or ticking. |
| `HeadquartersSetupComponent`, legacy receipt 1 / new receipt 2 | Existing `setupStarted`, `setupComplete`, `branchInitialized`, staff references/roles and placed records are preserved. New fields are explicit receipt version, `arrivalStarted`, `arrivalComplete`, observed arrival records and accepted supply summaries. Fresh setup assigns receipt 2 only before its first facility grant. |
| Existing company component | Scenario ID/version remain `async_industries`/1. Existing branch/funding idempotency and staff identities remain authoritative. A successful existing branch receipt returns Existing. |

Receipt 1 saves do not require the new arrival flag to retry company registration: their physical setup occurred under the old generator. Receipt 2 requires completed native arrival. Unsupported future receipt versions refuse a new initialization. Existing `setupStarted` stops facility replay; `arrivalStarted` stops stock/pawn replay. Loading a completed company does not require a new pregame setup receipt or rerun map generation. The selected surface tile is compared against the final receipt and never replaced by a random tile.

**Failure boundary:** the wrapper records objects observed on the map, not a complete transaction journal inside opaque native/third-party item factories. It cannot prove every requested supply successfully materialized when a native factory/placement fails. An interrupted native arrival is marked incomplete, keeps its known placements, and refuses a second grant; missing selected staff require retaining the failed save/log and starting a new campaign rather than inventing replacement pawns. This is not claimed as automatic recovery of all native generator exceptions. Branch registration can still be explicitly retried after a complete physical arrival without granting another roster, stock or allocation.

## Exact source basis

Pinned Core row 4 assembly SHA-256: `5CF1B5BE399D5B1C9C56CA72C9D35B4ECF307FEACF5859D04AC5A1AA5926356A`; local ILSpy `9.1.0.7988`. Optional EdB row 85 evidence and assembly hash are in the [provider source record](SCENARIO_AND_DOOR_PROVIDER_SOURCE.md#evidence-pins-and-reproducible-inspections). Decompiled text stays ignored in `.local/inspection-scenario/` and `.local/inspection-scenario-door/`; no decompiled code is included in the package.

- `RimWorld.Scenario.GetFirstConfigPage()` stitches scenario-part config pages in order and assigns `PageUtility.InitGameStart` to the final page. The company part follows the native pawn part in `RR_Scenarios.xml`.
- `RimWorld.PageUtility.InitGameStart()` calls `Find.GameInitData.PrepForMapGen()` **before** `Find.Scenario.PreMapGenerate()`. `Verse.GameInitData.PrepForMapGen()` removes entries beyond `startingPawnCount`, retaining the selected references/order. This is why the defensive `TryGetStaff` exact `SequenceEqual(candidates)` is valid after native trimming. The review page itself reads only the first selected count without removing optional candidates.
- `RimWorld.ScenPart_PlayerPawnsArriveMethod.GenerateIntoMap(Map)` enumerates native `PlayerStartingThings()` and actual starting possessions, and places the same starting pawns. Standing arrival uses native instant placement; no crash-pod thought is added. The review uses `GetSummaryListEntries("PlayerStartsWith")`, never the object-creating `PlayerStartingThings()` API.
- `EdB.PrepareCarefully.ControllerPage.StartGame()` prepares actual pawns, relationships and equipment, then opens the original native page's `next` and invokes its `nextAct`, bypassing native `CanDoNext`. The new separate next page therefore receives that known path. This is source evidence, not an observed compatibility result.
- EdB `ManagerEquipment.InitializeStateFromScenarioAndStartingPawns()` recognizes supplies with `is ScenPart_StartingThing_Defined`; `PrepareEquipment()` preserves non-replaced parts. The inspected path has no arrival-class equality filter and does not mark the custom arrival subclass replaced. `ControllerPage.ShouldReplaceScenarioPart` recognizes exact native starting/scatter thing classes; our fourteen parts are those native classes. EdB's later scenario restoration cannot cause Rimrooms stock replay because the saved receipt owns completion.

Additional UI source inspected: `RimWorld.Page`, with `PageTitle`, `DrawPageTitle(Rect)`, `DoBottomButtons(...)`, `PostOpen()` and protected `CanDoNext()`. Reproduce exact type inspection using the tool/assembly command in the linked source record; use `-t RimWorld.Page` with the pinned Core assembly. Existing local `PageUtility`, `GameInitData`, scenario and arrival inspections establish the order above.
