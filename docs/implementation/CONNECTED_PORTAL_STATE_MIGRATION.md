# Connected portal state and migration review

**Status:** read-only source review and migration recommendation; a saved portal graph and separate gate-opening API have since been added, but no ordinary cross-map job/crossing system is implemented by this review. The current expedition slice remains usable as historical/mission behavior, but it is not the connected-colony system required by [the portal contract](../CONNECTED_COLONY_PORTALS.md).

**Scope:** current campaign coordinate/site ownership, generated map parent, expedition component and transfer recovery, native gate binding and timed gate lifecycle.  No code, build, game, or save test was run for this review.

## Findings from current source

### Current service flow and hard coupling

- `ExpeditionComponent.Dispatch` is the only current player-facing route into the field (`OperationsExpeditions.DrawDispatch` calls it). Dispatch requires an idle expedition slot, a gate, a valid selected crew, a crew kit, an assigned operator, a campaign coordinate, a route recording, gate approach positions and a valid site; see [RimroomsExpeditionComponent.cs](../../src/RimroomsAsyncIndustries/Expedition/RimroomsExpeditionComponent.cs#L58) and [OperationsExpeditions.cs](../../src/RimroomsAsyncIndustries/UI/OperationsExpeditions.cs#L183).
- `DestinationService.EnsureSite(campaign, coordinate, out map, out entry)` is already directly callable without an expedition. It validates the branch coordinate, returns an existing owned map when valid, and refuses to reroll a previously opened/missing site; see [DestinationService.cs](../../src/RimroomsAsyncIndustries/Generation/DestinationService.cs#L31). It therefore supplies map resolution/generation to a future portal service, but it does not open an edge, move a pawn or provide a free-crossing entry path.
- `TickStaging` begins the gate opening with the expedition ID, starts the site component for that run, captures its manifest and synchronously transfers its selected crew. `TickField` then checks the same run, gate, site, return window and cargo capacity; see [RimroomsExpeditionComponent.cs](../../src/RimroomsAsyncIndustries/Expedition/RimroomsExpeditionComponent.cs#L258) and [RimroomsExpeditionComponent.cs](../../src/RimroomsAsyncIndustries/Expedition/RimroomsExpeditionComponent.cs#L298).
- Ordinary mission completion is coupled to crew return: `AllAtHeadquarters` leads to `Complete`, which calls `CloseOwnedOpening`; `Strand` also closes the opening. `ReturnWindowOpen` accepts only the matching `ActiveExpeditionId`, and emergency expiry strands a run. See [RimroomsExpeditionComponent.cs](../../src/RimroomsAsyncIndustries/Expedition/RimroomsExpeditionComponent.cs#L387), [RimroomsExpeditionComponent.cs](../../src/RimroomsAsyncIndustries/Expedition/RimroomsExpeditionComponent.cs#L450), and [ExpeditionClosure.cs](../../src/RimroomsAsyncIndustries/Expedition/ExpeditionClosure.cs#L245).
- `CompRimroomsGate.CanOpen`/`BeginOpening` require a nonempty expedition ID; gate ticks consume its opening window and can enter a finite emergency-return window after power, operator or time failure. `CloseOpening` records that run as last closed and clears the timer. `SpendOpeningTicks` and recovery receipts are also keyed by expedition ID. See [CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L301), [CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L323), [CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L346), [CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L387), and [CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L420).

## Minimum persistent model

The independent saved portal-network component planned under `Portals/` should be the authority for endpoint identity, connection identity and edge lifetime. Keep it branch-scoped and additive; do not store graph state in an `ExpeditionRecord` or duplicate `CoordinateRecord` ownership.

| Proposed record | Minimum stable saved data | Validation / authority |
|---|---|---|
| Portal endpoint | Stable `endpointId`; `branchId`; endpoint kind; optional `coordinateId`; persistent map owner reference/ID; map reference or a documented map-resolution route; provider/anchor reference and load ID; saved local cell and approach/orientation snapshot; endpoint record/version. For an HQ gate endpoint, link the exact native gate and its currently bound entry cell. For a generated coordinate endpoint, link the exact `RimroomsDestinationMapParent`, coordinate ID, and saved `EntryCell`/`ReturnCell`/`ReturnAnchor`. | IDs are unique within the branch and point to the same saved map owner/provider after load. Never derive the stable endpoint identity from a transient map tile, pawn, or current job. When a snapshot no longer validates, retain the record and report unavailable/recovery; do not silently retarget it to another door/cell. |
| Portal connection | Stable `connectionId`; `branchId`; source and destination endpoint IDs; connection kind (`Laboratory` or `NaturalPermanent`); edge schema/version; optional lab-gate reference; creation/discovery provenance and failure key. A permanent-natural edge records its permanent lifetime. A laboratory edge records its machine owner, while its live opening availability is derived from that gate's explicit portal-session API rather than a second graph timer/state counter. | Both endpoint IDs must resolve in the same branch; duplicates, self-edges where disallowed, broken references and malformed states disable that edge while preserving its record. A bounded route query uses a visited endpoint/connection set and fixed node/edge expansion budget; cycles are valid, unbounded traversal is not. |
| Crossing receipt | Stable operation/receipt ID; `connectionId`; direction; source and destination endpoint IDs; original pawn reference plus load ID; source/destination maps or parent IDs and cells; phase (`Prepared`, `Despawned`, `Arrived`, `NeedsRecovery`, `Committed`); saved tick/sequence; failure key. | Receipt is written before moving the original pawn, reconciled idempotently from actual custody/map after load, and never creates a second pawn or cargo owner. Actual carried inventory/carry items move with the pawn; separately hauled items remain actual objects in native hauling/carry ownership. |

The graph connection owns an edge, not a fresh copy of a site. The existing campaign coordinate list remains the authority for stable address, seed and generation versions. Because the current branch initializer creates only `AI-01`, a future discovery that introduces a new coordinate needs one additive campaign service such as `CreateDiscoveredCoordinate(stableDiscoveryId, sourceCoordinateId)`: derive the coordinate ID and seed deterministically from branch seed plus a persisted discovery/operation ID, insert exactly once, and return the existing record on replay. Then call `DestinationService.EnsureSite` before committing a new usable endpoint/edge. This API is not present in current source.

## Gate adapter recommendation

Keep the legacy gate path intact and introduce an explicit second operation mode for portal laboratory sessions. Do not pass a connection ID through `BeginOpening(expeditionId)` as if it were an expedition. That would make a connection masquerade as a mission and collide with current ID checks, power-debit receipts, recovery semantics, and automatic close calls.

Recommended adapter boundary:

1. Add a gate API specifically for portal connections (for example `CanOpenPortalConnection(connectionId)`, `BeginPortalOpening(connectionId, portalOpeningId)`, `CheckPortalCircuit(connectionId, portalOpeningId)`, and `EndPortalOpening(portalOpeningId)`). It reuses the existing HQ-only provider, assembly, calibration, operator, battery, threshold-power and actual entry-cell checks from [NativeGateBinding.cs](../../src/RimroomsAsyncIndustries/Gate/NativeGateBinding.cs#L108) and [NativeGateBinding.cs](../../src/RimroomsAsyncIndustries/Gate/NativeGateBinding.cs#L234), but it never creates or completes an expedition.
2. Keep three identities distinct: the permanent graph `connectionId`, the selected connection ID for the current machine opening, and a persisted `portalOpeningId`/sequence token for that physical opening session. A session token identifies the gate operation and debit receipts; it is not a persistent edge ID. Add distinct saved `rr_gatePortalConnectionId` and `rr_gatePortalOpeningId` fields (and an explicit owner kind if needed to make mutual exclusion unambiguous); leave `rr_gateActiveExpeditionId` legacy-only. `ObserveLaboratoryOpening` should match branch, gate reference, selected connection ID and opening session token explicitly, never treat the legacy `ActiveExpeditionId` as an edge key.
3. One gate can be the source endpoint for many saved addresses, each with its own connection ID and destination endpoint. Opening the machine to one address selects one connection for that session: that edge becomes available while the other remembered lab edges remain saved but closed. Do not bind all edges to the same opening token or delete/rewrite other destinations when one address is selected. If design later intends multiple simultaneously traversable apertures from one gate, it needs an explicit multi-aperture actuator model rather than ambiguous token reuse.
4. Keep exactly one persisted owner for laboratory opening duration, power debit, and gate failure/recovery state: the physical `CompRimroomsGate`. Its existing `openingTicksRemaining`, emergency/failure path, per-tick power check, and physical debit machinery are the appropriate single timer/electrical owner for both modes. The portal graph owns the persistent edge identity and endpoints; for a laboratory edge, open/closed route availability is derived from that edge's exact current portal session on its bound gate. Do not add another saved graph countdown or let graph observation start a second timer. Natural-permanent lifetime remains directly owned by its portal connection record and never uses the gate timer.
5. Preserve the existing scribed legacy field `rr_gateActiveExpeditionId` and all schema-2 `ExpeditionRecord`s as a legacy-exclusive mode. Add a saved owner-kind discriminator and distinct portal session/connection fields; reject simultaneous legacy expedition and graph connection ownership of one gate. On old saves, a nonempty legacy ID remains legacy-owned and must not be reinterpreted or automatically migrated. `HasUnresolvedNativeTrip` already blocks native-gate rebind while a non-closed expedition references that door; apply the same guard before selecting/opening a graph connection.
6. Give portal energy-spend idempotency receipts a portal-session namespace. Existing `NativeOpeningDebitId` uses `activeExpeditionId + nativeOpeningSequence`, and `GateWindowSpendReceipt` records an expedition ID. Reuse risks cross-mode receipt collisions. Validate a portal opening/session ID plus sequence and stable operation ID independently. Continue using the old receipt keys/API for active legacy runs.
7. Natural permanent edges do not call this gate adapter. Their persisted connection kind is permanent; do not use `openingTicksRemaining`, emergency-return ticks, operator presence, power debit, `BeginRecoveryOpening`, or `CloseOpening` to close them. A blocked door/cell makes passage temporarily unavailable, not the natural edge timed or deleted.
8. For a laboratory connection that loses power/operator or reaches its approved duration, the gate closes/fails its physical portal session; graph observation then stops offering new route assignments and route-dependent jobs are suspended/cancelled with reservations released. Pawns already on either map remain there with their actual inventories/items. Do not invoke expedition `Strand`, `Complete`, rescue-manifest or automatic-teleport paths for ordinary work.

### Active legacy runs during rollout

The safest additive migration is **no automatic conversion**. On upgrade, start the new portal component with an empty graph unless it already has valid portal records. Leave campaign coordinates/sites, the expedition component schema 2, gate legacy opening fields, receipts, recovery-held pawns, and all active `Staging`/`OnSite`/`Returning`/`Stranded` records untouched. `ExpeditionComponent` schema 1 migration only marks old cargo declarations for review and bumps its own schema; it does not reconstruct portal endpoints. See [ExpeditionClosure.cs](../../src/RimroomsAsyncIndustries/Expedition/ExpeditionClosure.cs#L245).

While a non-closed legacy run owns a gate, keep that run exclusive under its existing controller and do not attach a graph session to that gate. Its current time-limited return and explicit recovery behavior continue as-is. Once the run closes, the new portal service may bind a connection through the separate adapter. This preserves in-progress saves and uses the gate's one existing timer owner. Do not close or strand an active run just to seed the graph. An explicit, reviewed conversion can be considered later, but it needs a saved endpoint mapping and an acceptance migration; an expedition's coordinate/gate references alone are not sufficient evidence to invent one.

Closed expedition history and stale records remain readable. Stranded runs remain stranded and use the current recovery interface; the new persistent graph must not reinterpret `Stranded` as a permanent open edge or as proof that a pawn is at an endpoint.

## Entry path without an expedition

There is currently **no ordinary-crossing entry point**. The planned minimum is a graph-aware service and endpoint interaction that can be called without creating an `ExpeditionRecord`:

1. Resolve the pawn's actual current endpoint and branch; reject unavailable/foreign/invalid endpoint state.
2. Resolve a route through the saved graph with bounded search and validate every edge in the intended direction. For a natural edge, allow immediately when its endpoint is physically traversable. For a lab edge, require the saved connection to be open and its gate adapter to confirm the current physical circuit.
3. If target coordinate generation has not happened, resolve its existing `CoordinateRecord` and invoke `DestinationService.EnsureSite`; preserve the returned map, owner and stable entry cell. Do not publish a traversable edge until endpoint/map preflight succeeds. If creation fails, keep coordinate/edge identity and failure information, then retry the same seed/site rather than generating another coordinate.
4. Create a crossing receipt, physically move the same pawn and its actual inventory/carry state, verify destination ownership, then commit the receipt. On failure, reconcile actual pawn custody and either roll back or leave a recoverable receipt; never clone the pawn or delete a destination.
5. Connect this service to a map-aware cross-map job/route adapter. A button that transfers pawns directly can be an early diagnostic path, but it does not by itself satisfy native hauling, construction, bills, research, care, schedules, reservations or unified-colony behavior.

`Dispatch`, `QueueLoadout`, `CheckCrew`, `ExpeditionCargo.CheckKit`, `EnsureRouteRecording`, `FirstSliceSiteComponent.BeginOpening`, `Recall`, and mission return jobs remain useful optional mission behavior. They must not be prerequisites for the ordinary portal service.

## Failure and recovery rules to preserve

| Failure | Existing source behavior | Portal migration rule |
|---|---|---|
| Destination is already generated | `EnsureSite` returns the owned saved map after owner/fingerprint/cell/path validation. | Reuse its exact parent/map/entry; never reroll or make a parallel owner for the same coordinate. |
| Site generation fails before ready | Destination owner/coordinate graph and a failure key are retained. | Keep the stable coordinate and endpoint/edge discovery identity; retry that same site only through the explicit generation recovery rules. Do not mark an unusable half-edge as traversable. |
| A ready/opened site's map reference is missing | `EnsureSite` refuses the reroll and returns a retained failure. | Keep the connection record but mark its route unavailable for recovery; do not replace the map under active pawn/item ownership. |
| Endpoint anchor/cell is obstructed | Current destination validation requires entry, return and evidence locations reachable. | Preserve the endpoint and connection. Suppress that crossing direction until the same saved provider/cell is repaired or explicitly recovered; never retarget automatically. |
| Laboratory connection closes while pawns are remote | Current mission route can emergency-recall then strand/close the gate. | Cancel/suspend route jobs and release reservations; actual pawns/items stay on their current map. Reopening reconnects the same endpoints. |
| Save/load interrupts crossing | Existing transfer receipt has source-only recovery, scoped to a run. | New receipt must encode target/direction and phase and reconcile actual spawn/holder state exactly once. Keep the old recovery path for old runs. |
| Natural edge is blocked or an endpoint fails validation | No natural portal state exists yet. | Keep the saved permanent-natural declaration; obstruction or corruption affects immediate route eligibility/recovery, not its lifetime or permanence. |
| Multiple paths/cycles | Current room planner validates only the bounded 6–8 room local graph; no inter-site graph exists. | Permit connection graph cycles, use visited IDs and fixed route-query budgets, and report no path when the budget is reached. Never search an unbounded procedural frontier in one tick. |

## Review of the additive gate-opening API

The current source adds `rr_gatePortalConnectionId`, `rr_gatePortalOpeningId` and a saved sequence in [PortalGateOpening.cs](../../src/RimroomsAsyncIndustries/Gate/PortalGateOpening.cs#L9). `BeginPortalOpening` validates a laboratory edge, branch, first gate endpoint and native designation; it reuses the gate's physical readiness/timer and asks the graph to observe the exact connection/opening IDs. The old `rr_gateActiveExpeditionId` save key remains separate in [CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L119), and expedition closure still closes only a gate whose active legacy ID matches that run ([RimroomsExpeditionComponent.cs](../../src/RimroomsAsyncIndustries/Expedition/RimroomsExpeditionComponent.cs#L470)). This supports the additive legacy-preservation direction; it is source evidence, not a migration/runtime test.

The first review findings are now resolved in the gate source, pending runtime verification:

- `RecoverPortalOpening` checks the same connection/session, waits until the emergency window expires, checks native recovery energy, spends it with a stable operation ID and records a `PortalOpeningRecoveryReceipt`; replay returns `Existing` only for the matching opening. `ClosePortalOpening` refuses emergency close, preventing close/reopen from bypassing the recovery cost. See [PortalGateOpening.cs](../../src/RimroomsAsyncIndustries/Gate/PortalGateOpening.cs#L116).
- `ValidatePortalOpeningOwner` now runs during post-load and faults split/whitespace connection-opening IDs, simultaneous legacy and portal ownership, invalid portal sequence state, malformed receipts and duplicate recovery operation IDs. The fault disables gate ticking/readiness/open/close/recovery while retaining saved values. Historic receipts may refer to earlier closed openings and are intentionally not required to match the current opening. See [PortalGateOpening.cs](../../src/RimroomsAsyncIndustries/Gate/PortalGateOpening.cs#L42) and [CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L140).
- Generic public `CloseOpening()` is now legacy-only; `ClosePortalOpening(connectionId)` validates its owner before calling the private close core. The initial close-bypass finding is resolved in source ([CompRimroomsGate.cs](../../src/RimroomsAsyncIndustries/Gate/CompRimroomsGate.cs#L348), [PortalGateOpening.cs](../../src/RimroomsAsyncIndustries/Gate/PortalGateOpening.cs#L105)).

`RimroomsPortalNetwork.Availability` now calls `HasUsablePortalWindow(connectionId, openingId)` for laboratory edges, so the fresh operator/power/window check is wired into source-level route eligibility ([RimroomsPortalNetwork.cs](../../src/RimroomsAsyncIndustries/Portals/RimroomsPortalNetwork.cs#L153), [PortalGateOpening.cs](../../src/RimroomsAsyncIndustries/Gate/PortalGateOpening.cs#L23)). The gate findings from this review are resolved in source. No game/save/build test was run, so these changes remain unverified at runtime.

## Implementation sequence and acceptance boundary

1. Add and save the branch-scoped portal graph/endpoint/connection records and validators under `Portals/`; ensure normal Core-only saves with no branch get an inert empty graph.
2. Add deterministic campaign coordinate-discovery creation and one endpoint resolution path to existing `DestinationService` site owners.
3. Add the disjoint gate connection adapter with explicit owner-mode checks and one authoritative lab timer; retain existing legacy expedition APIs and save keys.
4. Add durable crossing receipt/reconciliation, then a direct ordinary route interaction that needs no expedition, selected crew, operator-as-traveler or cargo manifest.
5. Add bounded route planning and one cross-map job type at a time, preserving native work policies and reservations. Expand the acceptance matrix only after evidence for each supported work/provider family.
6. Record runtime save/reload/transfer-fault tests for both directions, route cycles, blocked endpoints, power/operator loss, lab closure/reopen, permanent-natural persistence, and a save containing an active legacy expedition. Full unified-colony behavior and connected-site streaming remain open until these checks and the work adapters are implemented.

This review identifies the ownership/API boundary. It does not establish runtime compatibility, implement a portal graph, or claim that the full connected colony is complete.
