## Findings that constrain the design

| Topic | Source fact | Design treatment / limitation |
| --- | --- | --- |
| Vanilla `Site` map size | `RimWorld.Planet.Site.PreferredMapSize` starts at `(200,1,200)` and takes the maximum with each part's `minMapSize`; it has no path to reduce the default. `CaravanArrivalAction_VisitSite` asks for that preferred size. | Do not use the normal Site visit path for AI-01's required 60×60 map. Use a project-owned map owner and an explicit size. Vanilla Site cleanup rules also do not match the required saved-coordinate lifecycle. |
| Sized map-generation API | `Verse.GetOrGenerateMapUtility.GetOrGenerateMap(PlanetTile tile, IntVec3 size, WorldObjectDef suggestedMapParentDef, IEnumerable<GenStepWithParams> extraGenStepDefs = null, bool stepDebugger = false)` returns an existing map at the tile or creates/uses a `MapParent` and calls `MapGenerator.GenerateMap(size, parent, parent.MapGeneratorDef, parent.ExtraGenStepDefs + extras, ...)`. The overload without `size` uses the world's initial map size. | A finite surface-map route exists for 60×60: pass `new IntVec3(60, 1, 60)` explicitly. Give every coordinate a valid, unique tile and a stable `MapParent`; `Game.FindMap(tile)` returns the first loaded map with that tile, and `WorldObjectsHolder.MapParentAt(tile)` likewise selects by tile. Duplicate tile ownership can return the wrong map/parent. `CoordinateRecord.site.Tile` can be the persisted tile association, but tile allocation/reservation is still a design decision. |
| Map identity and one-map-per-parent | `MapParent.Map` resolves with `Current.Game.FindMap(this)` and `HasMap` tests that result. `MapGenerator.GenerateMap` sets `map.info.parent = parent`; if the supplied parent already owns a map, it logs an error and clears the parent argument rather than generating a second map for it. | Check and reuse the coordinate's existing `site` and map. Never call `GenerateMap` a second time for an already mapped parent. Store the coordinate ID, explicit seed inputs, generator/library versions, and final room graph before first generation; keep the generated map authoritative afterward. |
| Stable map owner save route | `WorldObjectMaker.MakeWorldObject(def)` instantiates `def.worldObjectClass`, assigns a world-object ID, and calls `PostMake`. `WorldObjectsHolder.Add` registers it. `WorldObjectsHolder.ExposeData` deep-scribes saved world objects, and `WorldObject.ExposeData` saves its def, tile, ID, and component state. `Game.ExposeData` deep-scribes all maps; `Map.info.parent` links each map to its owner. | The custom `WorldObjectDef` must be saved and its owner/component state must persist the coordinate association. Set the valid tile before `WorldObjectsHolder.Add`; do not rely on its invalid-tile fallback. The branch coordinate record should keep the parent reference and stable identity; the map is the physical state owner. Save/load cross-reference and revisit still require runtime verification. |
| Map seed is not the project seed contract | For ordinary maps, `MapGenerator.GenerateMap` seeds generation from `Find.World.info.Seed` and `parent.Tile`; pocket maps use the world seed and parent world-object ID. Each GenStep then receives a seed derived from that map seed and its `SeedPart`. | Core does not automatically consume the branch seed or coordinate ID required by the procedural-space contract. Generate the bounded layout from the saved branch/coordinate/version inputs using a project-owned deterministic routine, persist the chosen graph before map generation, and have the GenStep place that graph. Do not claim that tile, world-object ID, or current RNG order implements the contract. |
| Generation order and failure handling | `MapGenerator.GenerateMap` assigns `map.info.Size` before `ConstructComponents`; invokes the optional pre-content initializer; composes generator, tile-mutator, biome, and extra steps; adds the map to `Current.Game` before contents generation; then calls each GenStep in `order`/`index` order. It calls `Find.Scenario.PostMapGenerate(map)` unconditionally after the steps, then finalizes the map and notifies the parent. `GenerateContentsIntoMap` catches/logs each GenStep exception and continues. | Keep scenario effects guarded to the intended HQ/start map. Use a deliberately small generator definition and audit biome-added steps for the chosen tile; the map is not only the project's GenStep. Preflight graph geometry and all required placements before adding a parent/generating. A returned `Map` or absence of a thrown exception is not proof that the custom site completed: verify entry, return anchor, room bounds, required objects, and routes before dispatch; on failure keep the gate closed and expose a recovery state. |
| Map retention/removal | `MapParent.ShouldRemoveMapNow(out ...)` defaults to `false`; its tick calls `CheckRemoveMapNow`. `MapParent.PostRemove` deinitializes its map. `MapParent.Destroy` calls `Notify_LeftBehind` on map things, and `Game.DeinitAndRemoveMap` deinitializes/removes the map. `Site.ShouldRemoveMapNow` can remove its map after threat/condition and blocker checks, then may remove the Site object. | A project-owned `MapParent` is the safer owner for a revisitable coordinate. Do not call `Destroy`, `WorldObjectsHolder.Remove`, `DeinitAndRemoveMap`, or `PocketMapUtility.DestroyPocketMap` while an expedition, pawn, carried/loose cargo, or recovery state refers to the destination. The default owner will retain the map; explicit cleanup must first verify all project-owned occupancy/manifest conditions and preserve a recoverable coordinate record. |
| Map lifetime and scale | Maps remain in `Game.Maps` until explicitly removed; switching `CurrentMap` does not remove them. `Game.UpdatePlay` invokes `MapUpdate()` for every map. `Game.AddMap` rejects an add when the current count is greater than `127`, so the list can reach 128 maps (including the HQ and any other maps) before later additions are rejected. | This is persistent-in-memory map ownership, not unload-on-return. Keep the first slice to one destination and define a campaign map budget before expanding to many coordinates. A larger campaign needs either a tested, lossless archive/restore design or an explicit bound; never silently discard a visited map. Measure retained-map update and save/load cost on the target machine. |
| Vanilla site return entry | `CaravanArrivalAction_VisitSite` generates/reuses a map through `GetOrGenerateMapUtility`, then `CaravanEnterMapUtility.Enter` moves the caravan's existing Pawn objects onto it. Its default inventory mode is `DoNotDrop`; it removes/destroys the caravan after transfer. `CaravanExitMapUtility.ExitMapAndCreateCaravan` builds a caravan from the supplied Pawn objects and calls `Pawn.ExitMap`. | This is a source-backed identity-preserving world-caravan route, but it represents world travel and is not the machine's direct gate transition. It carries pawns and their pawn-held inventory through the caravan. It does not automatically move arbitrary loose destination-map items with the crew. Runtime checks must include each pawn's `thingIDNumber`, inventory counts, and explicit cargo manifest on both sides. |
| Vanilla direct portal pattern | `RimWorld.MapPortal` lazily creates one pocket map in `GetOtherMap`; `PocketMapUtility.GeneratePocketMap` creates a `PocketMapParent` linked to the source map. The portal serializes its pocket-map and exit references. `PocketMapExit` points back to the entrance. `JobDriver_EnterPortal` despawns the same Pawn and spawns that Pawn on the other map. `PortalContainerProxy.TryAdd` sends the same Thing through `GenDrop.TryDropSpawn`. | This is a useful Core-code reference for direct transitions and identity-preserving transfers. The inspected entry building stores one pocket-map reference; it is not a multi-coordinate registry. A reusable corporation gate needs a saved per-coordinate owner/reference rather than overwriting the sole destination reference. The vanilla first-entry map generation is synchronous inside the pawn job, so pre-generate and validate before moving any crew to avoid an entry-time stall or a partial crew transition. |
| Fog and room discovery | `FogGrid.ExposeData` serializes a map-sized bit array; `Map.ExposeData` saves the fog grid. | Native fog can supply the cell visibility layer and survives with the map, but it does not represent the contract's stable room IDs, survey states, route history, or Branch-owned discoveries. Keep those in explicit project state (`CoordinateRecord.rooms`/map component) and update them from observation actions. |

## Recommended bounded first-slice route

1. Before creating the owner, form a deterministic six-to-eight-room graph from the persisted branch seed, coordinate ID, generator version, room-library version, and bounded layout choices. Validate bounds inside a 60×60 rectangle, doorway/link agreement, connectedness, safe entry and return cells, and reachability of all required areas. Write the resulting room records to the coordinate; keep the explicit seed inputs even after the graph is saved.
2. Assign the coordinate a unique, valid `PlanetTile`, create a project-owned saved `MapParent` from its `WorldObjectDef`, set its tile, register it, and store the returned reference in `CoordinateRecord.site`. The tile must not already own another loaded map or the wrong map parent. Keep the coordinate-to-owner association for save/load and revisit.
3. Request the map with `GetOrGenerateMapUtility.GetOrGenerateMap(tile, new IntVec3(60, 1, 60), RR_BackroomsSite, extraGenStepDefs)`. Use a curated map generator and a custom GenStep that places the saved graph and original project objects. Because vanilla biome and scenario generation also run, inspect the selected tile's added GenSteps and make unrelated scenario effects no-op on this destination.
4. Before dispatch, verify that the map is exactly 60×60, all six-to-eight saved room IDs have valid placed bounds and links, the crew spawn and return marker exist, and each mandatory objective is reachable. Keep the machine closed on failure; do not spend, move pawns, consume cargo, or reroll a graph already shown to the player.
5. Let the expedition layer perform a single journaled transfer using the same Pawn and Thing objects, followed by reconciliation of source/destination ownership and the physical manifest. Keep the destination's `MapParent` and map until the expedition has returned and no pawn, carried/loose cargo, or recovery record can refer to it. A direct map transfer is not supplied by `GetOrGenerateMapUtility`; the gate/expedition implementation owns that transaction.
6. On revisit, use `coordinate.site` and its existing map. If a previously generated/visited coordinate has lost its map, report a recovery error and preserve its coordinate/room/case records rather than silently generating a fresh instance. Never use the current generator version to reroll that coordinate.

These APIs make the route plausible from Core source; the source review does not prove that the content XML loads, the `MapParent` is picked up correctly by a real save, the map is deterministic, a 60×60 map performs well, or custom transfers are failure-atomic.

## Remaining runtime evidence

The project owner must run the Core-only first playable profile before treating these points as complete:

- Generate an AI-01 map at exactly 60×60 with six to eight rooms; check safe entry/return, links, all required object placements, no blocked mandatory path, and no unrelated scenario start effects.
- Reopen the same coordinate during the same session and after save/load; compare parent/map identity, room IDs/bounds/links, terrain, player edits, contents, fog, and event state. Re-run after creating another coordinate to detect seed/order coupling.
- Move a three-pawn crew plus the one shared field loadout and evidence case through the gate and back. Compare pawn and Thing IDs, stacks, inventories, equipment, and source/destination manifests before and after; interrupt or fail the transition to verify recovery without loss or duplication.
- Attempt every owner-removal path while a pawn, item, expedition manifest, or recovery state remains; prove the site cannot disappear. Verify cleanup only after a completed, empty expedition if cleanup is later implemented.
- Save/load mid-expedition and revisit; confirm all map and room discovery state remains. Profile map generation, transitions, retained-map updates, and saves on the named test machine.
- Exercise a deliberately invalid layout/template input and a GenStep error; prove the gate stays closed and the player receives a recoverable failure rather than a partial or rerolled site.
