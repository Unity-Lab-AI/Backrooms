## Accepted rules and bounded player flow

- The Company Account is a branch-local USD ledger. The parent corporation's multi-trillion-dollar valuation is setting context, not spendable stock. A dollar balance never creates silver or other cargo.
- A purchase starts with an inspectable quote for a real Core `ThingDef`, positive quantity, total USD price, current expected stack count and mass, proposed dispatch/delivery timing, receiving location, and cancellation rule. Preserve the quote values at acceptance; no settlement-time reroll.
- The player selects an HQ receiving area/stockpile that permits the item. Use a small Core-only procurement catalog and one item line per order for this increment. Item selection and price entries remain editable proposals from the economy workbook, not owner-approved final balance values.
- **Proposed first-slice cancellation rule:** an accepted order can be canceled before supplier dispatch for the explicitly quoted full refund (zero cancellation fee in this increment). Once dispatched, the order cannot be canceled in this slice; the player may hold/retry its undelivered cargo. Delivered items are not removed or refunded by cancellation. Display this rule before acceptance.
- Acceptance records one stable order ID and debits the quoted amount once. A supplier dispatch owns real item stacks, not a virtual quantity counter. Delivery places bounded stacks into the selected receiving area or staging cells. Pawns then use ordinary RimWorld haul jobs to move those items into storage.
- If receiving space accepts only part of a shipment, record a receipt for only the observed physical quantity placed. The unreceived physical stacks remain held by the saved shipment owner and the order remains partially delivered; retry does not create or charge for a second copy.
- If no valid receiving route exists, do not spawn a stack or mark delivery complete. Keep the paid shipment visible and recoverable, and report whether it is waiting on a filter, a reachable cell, staffing/hauling, or map capacity.

The bounded first implementation can use one small catalog and a single local supplier route. It should not promise a general storage-mass limit: Core storage is organized around cells, filters, priorities, stack compatibility and reachable haul destinations, not a single warehouse-capacity number.

## Transaction and state contract

The current branch service is `RimroomsCampaignComponent.PostTransaction(string operationId, long amountUsd, string reasonKey, string relatedId)`. It is idempotent by operation ID: a repeat with the same amount, reason and related order returns `Existing`; a mismatch refuses; insufficient funds and overflow refuse without changing the balance. Implement orders in the campaign/branch owner and reuse this transaction route rather than creating a second balance system.

1. Allocate and save a stable order ID using the branch ID plus a saved monotonic sequence. Snapshot supplier/item/quantity/quote/ETA/receiving target/cancellation terms and the accepted quote amount.
2. Charge with operation ID `<orderId>:purchase`, related ID `<orderId>`. On an exact ledger retry, recover the existing order; never create a second shipment just because payment returns `Existing`.
3. Keep order lifecycle and receipt IDs stable: `<orderId>:dispatch`, `<orderId>:delivery:<batch>`, and `<orderId>:cancel`. A delivery receipt records requested and actually placed counts per item, spawned Thing references/load IDs, location, tick and remaining shipment-owner count. Mark the order complete only when the actual manifest has been received.
4. A pre-dispatch cancellation credits the quoted refund with one stable `:cancel` transaction. A post-dispatch order remains paid and recoverable; this increment does not destroy the held remainder or refund already delivered items.
5. On load, reconcile order state, ledger entries, held Thing stacks, map-spawned shipment items and delivery receipts. If they disagree, stop automatic debit/refund/creation and expose a recovery state. There is no database-style atomic transaction across the ledger, item holder and map; stable receipts and reconciliation are required.

## Failure handling and acceptance evidence

Refuse an invalid catalog item/quantity, expired/mismatched quote, duplicate ID with different terms, insufficient funds, missing HQ map/receiving target, disallowed item filter, blocked or unreachable cell, or malformed cargo. Show actual order/ledger IDs and the missing requirement. A partial placement records only the placed count and retains the rest; a retry does not reprice, re-debit, duplicate, or erase cargo. If the active stack setting changes, item count and total price stay fixed while the stack estimate updates from the current Def. Preserve Core-only operation when OgreStack and storage rows 122/259 are absent.

Owner-launched acceptance remains post-implementation work: Core-only and OgreStack default/actual-preset profiles; quote and purchase retry; insufficient funds; cancel before and refuse after dispatch; full, partial and zero receiving capacity; blocked/filter-denied destination; native pawn haul to stockpile; stack-setting change between quote and dispatch; save/reload at accepted, in-transit, partially delivered and complete states; compare ledger operation IDs, shipment-owner counts, map Thing counts and receipt counts. Then repeat focused full-profile cases with rows 122/259. Use disposable saves, record exact game/Core hash, DLC, mod order and OgreStack saved preset/overrides; do not launch tests before the owner starts the profiles through RimSort.
