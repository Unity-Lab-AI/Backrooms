# Connected-colony work: pinned Core API and implementation route

**Date:** 2026-09-28. **Evidence:** local source inspection only. No implementation, compilation, tests, game, profile change or Git operation. This review owns only this document; decompiled text is ignored local reference material.

## Task and decision

Read [CONNECTED_COLONY_PORTALS.md](../CONNECTED_COLONY_PORTALS.md), [AGENTS.md](../../AGENTS.md), [regression containment](../REGRESSION_CONTAINMENT.md), the [native gate implementation](PHASE_3_NATIVE_GATE_IMPLEMENTATION.md) and the earlier [expedition transfer record](PHASE_2_EXPEDITION_IMPLEMENTATION.md). Features: RR-GATE, RR-EXP, RR-STA, RR-FAC, RR-SPACE, RR-COMPAT. The governing contract requires automatic work/material/needs access through open portals, without mandatory dispatch. Natural links are permanent; laboratory availability is infrastructure-owned. Existing expedition timers and selected-crew rules cannot own this network.

**Recommended route:** a branch-owned portal graph and saved map-aware work intent, executed as real local job stages. Travel through endpoints with the original pawn and its real cargo, then reacquire local reservations and execute the appropriate native job on the actual destination map. Implement explicit adapters for each work/need family. Do not pass a remote target to an arbitrary native WorkGiver and assume it is a valid preview.

**Why:** native scanning, pathfinding, reservation managers and many validators use `pawn.Map`; cell job targets have no map. `Pawn.DeSpawn` stops jobs and clears reservations. A native job/driver cannot simply continue across a Map boundary. This is a connected scheduler and logistics layer, not a global stock-count patch.

## Two candidate integration architectures

### A. Core-only staged adapters — recommended initial foundation

Implement custom WorkGiver/ThinkNode extensions, JobDefs and saved intent/crossing services. Insert the narrowly scoped nodes with native XML patches at the relevant existing work/needs decision points; ordinary local behavior remains available. For each work type, rank remote supported intents using the same enabled work type, capacities, manual priorities and within-type order, then route to a real local native job. Food/rest adapters must preserve their native priority context and emergency/constant-tree precedence. This is not a low-priority catch-all that forever starves remote higher-priority work behind local lower-priority chores.

Core provides the public virtual node/workgiver and custom JobDriver extension points, so **Harmony is not intrinsically required** for saved graph, crossing, staged physical logistics or explicitly integrated Core work families. Map-aware remote preflight still has to be written for each supported family; native private helpers are not safe generic remote evaluators. XML replacement/insertion also requires compatibility review when other mods replace those think trees. Native class/state cloning and full copied vanilla implementations are unnecessary and prohibited.

### B. Same intent engine with narrow scheduler/provider Harmony adapters

An optional integration layer could hook specific native/mod job selection and candidate/reservation entry points, leaving the real pawn on its actual map throughout. It can compare remote plans with local results and integrate providers whose private search paths lack a usable extension. Each patch needs an exact installed signature, method-order review and explicit compatibility record. A JobGiver_Work postfix that acts only on NoJob would miss remote higher-priority work; a GetRest fallback after NoJob would miss remote beds because native ground sleep usually returns a job. Those shortcuts are incomplete.

This approach may reduce think-tree replacement conflicts but increases dependency and patch-order risk. Harmony alone does not solve map-local driver/toil/region assumptions. Do not introduce it as a mandatory Core-only dependency without reconciling that project boundary; the reviewed Core-only route remains the initial fallback. No architecture here establishes universal compatibility with installed workgivers.

## Preservation failures to guard and acceptance limits

- Reusing a native driver/queued LocalTargetInfo after crossing can address the wrong map cell, lose reservation or repeat a consumption/finalizer. Never spoof `pawn.Map`, clone a pawn or share one job instance between independent owners.
- Remote native HasJob/JobOn probes can read the wrong map, update ingredient-search throttles/static caches or trigger permission/history notifications. Preview only through explicit safe adapters.
- Blind cargo restoration can duplicate split stacks, lose merged-item identity, drop a casualty or bypass OgreStack/capacity. Follow actual counts/holders and never reconstruct cargo from a Def/count manifest.
- Calling GenSpawn with a Def creates another object; permissive spawn/wipe can alter blockers. Retain an original-object recovery holder on failure and refuse an unsafe destination.
- Broad reservation overrides can grant two workers the same quantity; remote planning leases do not replace native local reservations. Preserve real custody and final revalidation.
- A scheduler running outside native urgency can interrupt hunger, sleep, danger, drafted/mental-state restrictions or player orders. Do not mark automatic work forced. Allowed areas, locked-door policies and custody must be checked for every segment/map.
- Physical construction material delivery, bill/UFT progress, research, tending and needs completion remain native local actions. Neither a shared resource counter nor a successful single hauling demonstration satisfies the contract.

Future owner-launched cases must cover both directions and chained/cyclic links, permanent natural versus powered laboratory lifetimes, local/remote competing priorities, work schedules/areas/danger/forbidden/locks, occupied reservations, stack splits/merges and loaded OgreStack limits, ordinary/mod storage, construction/UFT/bill edits, medical custody and urgency, food/rest, closure before/after pickup and during crossing, death/downing/mental break, save/load at each segment and failed spawn recovery. The full profile and RWT branch separation need separate records. No runtime compatibility or completed connected-colony feature is claimed by this source review.

## Follow-up review: initial portal graph source

At the lead's request, read [PortalConnectionRecord.cs](../../src/RimroomsAsyncIndustries/Portals/PortalConnectionRecord.cs) and [RimroomsPortalNetwork.cs](../../src/RimroomsAsyncIndustries/Portals/RimroomsPortalNetwork.cs) without editing either. This is the initial graph increment, not the scheduler/crossing implementation. The lead was independently updating laboratory opening identity during this review; no obsolete expedition-identity observation is asserted as a final defect.

Source-supported preservation: records save Map/Thing references and endpoint cells; moving/replacing an anchor does not silently retarget a connection. Registration rejects identity conflicts, same-map edges and an unknown destination coordinate. Natural availability does not use a timer, operator, battery or mission. The route finder traverses both directions, uses a visited-map set and returns a distinct SearchBudgetExceeded result. The graph neither creates objects nor changes pawn/job/cargo ownership. No direct duplication or destructive recovery path was found in these two files.

Two bounded-search integration issues should be resolved before this becomes a per-pawn automatic scheduler:

1. `FindRoute` counts its outer edge iterations, but `Availability` calls `Owned`, which calls `connections.Contains(edge)` for each relevant edge; ownership/site checks also scan coordinate/map collections. Thus the declared connection budget does not bound all underlying work independently of total graph size. Build validated membership/adjacency indexes and charge candidate validations consistently, or explicitly bound and measure the nested work. This is a source-level complexity finding, not a measured slowdown.
2. A budgeted call has no continuation state. Repeating the same request with the same limits restarts at the beginning; a reachable route beyond that prefix cannot make progress. Until a saved/transient bounded search cursor or deliberate bounded escalation exists, callers must expose pending/budget-limited status and must not equate it with NoRoute.

Endpoint boundary: `ValidDoor` currently accepts any `Building_Door` with a cardinal-adjacent approach to its center, while `Availability` checks approach standability. It does not establish pawn-specific access, allowed area, forbidden/lock rules, approach-to-door pathing or a multi-cell provider's true opening footprint. That is acceptable as a topology-only predicate only while the caller still performs those checks before crossing. Wide/modded door support needs its exact provider adapter; this check alone is not that support. Laboratory endpoints additionally recheck the designated gate's current entry cell. Original door rotation is not separately saved for natural anchors, so a future crossing implementation must define and validate which physical side the saved approach represents.

These observations do not change the recommended staged architecture or close any connected-work acceptance item. No code, build, test or runtime operation was performed for this follow-up.

The query retains capture position, available-edge adjacency, BFS queue/visited maps, current neighbor cursor, predecessor chain and final-validation cursor. Capture, neighbor examination, map-queue changes, path reconstruction/copy and availability revalidation consume operations. Each call processes at most `min(maxOperations, 1024)` operations. Nonpositive budgets return InvalidState. Repeated small calls therefore progress on a stable graph, including a graph too large for one call. Revalidation covers closed/missing edges as well as successful ones; a newly available edge invalidates and restarts the search. Natural links remain untimed. Laboratory checks now also reject the lead's `HasPortalOwnerFault` conflicting-owner state.

**Resolved source findings:** membership uses the lead's HashSet rather than per-edge linear Contains; per-query adjacency removes the old full connection-list scan for every visited map; cursor continuation removes deterministic prefix starvation. The old `FindRoute(Map,Map,int,int,out IReadOnlyList<PortalRouteStep>)` remains as a deliberately single-pass compatibility wrapper. It retains its map-count cap, treats its connection argument as an operation budget including capture/validation, and maps Pending/Invalidated to SearchBudgetExceeded, never NoRoute. Automatic callers must use the resumable API.

**Preserved state and remaining limits:** schema-1 saved connection fields and Register/Observe signatures are unchanged. Query buffers are replaced on invalidation; they do not modify saved edges, prior returned route lists, maps, jobs, pawns, cargo or reservations. The route is a shortest-hop topology result, not a pawn-specific or lowest-travel-cost path. An availability call still includes native geometry and coordinate/map ownership collection checks; operation counts are not exact CPU/time bounds. Collections and allocation/GC have their normal amortized costs. Query storage is proportional to captured graph size; the scheduler must bound concurrent queries and its total per-tick budget. A continuously changing graph may repeatedly invalidate. Because a bounded validation sweep can span ticks, any result is an observation, not an atomic enduring snapshot: every actual traversal must use the live validation API. No automatic scheduler, traversal or job adapter is supplied by this change.

The lead's final gate integration adds `HasUsablePortalWindow(connectionId, openingId)`. Laboratory Availability now calls it for live owner/session, remaining-time, operator/station, circuit and next-tick battery checks; it does not rely only on last tick's saved open flag. Observe retains its identity checks. This prevents a topology traversal check accepting newly lost power/staff before the gate's next tick observes that loss.
