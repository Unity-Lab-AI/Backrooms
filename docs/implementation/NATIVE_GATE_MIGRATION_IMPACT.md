# Native door gate migration impact

**Purpose:** bounded source map for replacing the custom gate/console/cutoff/generator objects with opt-in Core objects while preserving the dispatch and return contract. This is a design and source review only. No code, build, profile, or game behavior was changed or verified here.

**Binding direction:** follow [existing-content-only gameplay policy](../CONTENT_REUSE_POLICY.md) and [regression containment](../REGRESSION_CONTAINMENT.md). Use a native door as the threshold, a specifically linked CommsConsole as the station, and a specifically linked Core Battery for real stored energy. A mapped object remains opt-in; installing Rimrooms must not silently turn every colony door into a gate.

The inspected Core pin is RimWorld `1.6.9676.17735`, `Assembly-CSharp.dll` SHA-256 `5CF1B5BE399D5B1C9C56CA72C9D35B4ECF307FEACF5859D04AC5A1AA5926356A`; see [Phase 2 work/power source review](PHASE_2_WORK_POWER_SOURCE_REVIEW.md). Native routes verified from that pin and Core Defs:

- Core `Door` and `Autodoor` both use `RimWorld.Building_Door`. `Door` has no `CompPowerTrader`; `Autodoor` inherits the door class and has a native trader with `basePowerConsumption=50 W`. `Building_Door` exposes `Open`, `HoldOpen`, `DoorPowerOn`, `StartManualOpenBy(Pawn)`, and `StartManualCloseBy(Pawn)`; its `DoorOpen(int)` implementation is protected. A door's open/close state is ordinary map passage, not the saved expedition window. Prefer Autodoor for a powered Core threshold; do not infer portal state from `Open`.
- Core `CommsConsole` uses `Building_CommsConsole`, has a native 200 W `CompPowerTrader`, `CompFlickable`, and breakdown comp, and exposes `CanUseCommsNow` and `GiveUseCommsJob(Pawn, ICommunicable)`. Its standard faction/trader communications must remain available. Add the Rimrooms station action beside that route; do not hijack `UseCommsConsole` or assume it has a bill stack.
- Core `Battery` uses `Building_Battery` and `CompPowerBattery`. Verified members include `StoredEnergy`, `AmountCanAccept`, `Props.storedEnergyMax`, `AddEnergy(float)`, and `DrawPower(float)`. `PowerNet.powerComps` and `.batteryComps` are public in this pin; `CurrentEnergyGainRate()`, `CurrentStoredEnergy()`, and `CanPowerNow(CompPowerTrader)` report aggregate network conditions, not a reservation for one device. Core's `PowerNetTick()` charges/discharges network batteries. `CompPowerBattery.CompTick()` also self-discharges at 5 W.

## Recommended provider boundary

Preserve the public gate operations in `CompRimroomsGate` as the single integration contract; change its provider lookup and power/state implementation behind that contract. Avoid a second campaign balance, expedition owner, or parallel gate timer. If the implementation splits the component into a native provider class, introduce one narrow `IRimroomsGateAccess` resolver and convert every typed caller listed below in the same change. In either design, access must resolve from the saved selected gate reference.

1. Map an existing Core `Autodoor` as the first powered Core threshold. If attaching gate logic through a Core Def patch, keep the added component dormant until the player designates that exact door in a Rimrooms facility. Do not auto-bind neighboring doors. A plain Core `Door` remains a manual, unpowered threshold and must not be reported as having Autodoor power behavior.
2. Let the gate binding save explicit references to the selected door, selected `CommsConsole`, and selected `Battery`. Replace nearest-Def scans with those references and validate spawned/map/HQ identity, component presence, powered/flick/breakdown state, and the required network relationship before work or dispatch. Missing or destroyed links refuse with a visible recovery route; do not select a replacement silently.
3. Recast `CompRimroomsGateConsole` into two roles if necessary: the native CommsConsole is the control/operator station and keeps its own native comms behavior; an existing Core `Building_WorkTable` (player-designated) is the assembly bill giver. Keep calibration/staff jobs reserving the actual linked CommsConsole and its interaction cell. Do not call the native CommsConsole a bill giver or drop the one-shot material/work completion guard without an explicit contract change.
4. Replace `GateEntryCell`'s custom-gate `InteractionCell` assumption with a saved, reachable threshold-side cell derived from the selected door's rotation and validated against the map. Add it to each new expedition record as a new Scribe field, captured at dispatch; old runs derive a fallback from their saved gate ref only when needed. Do not rewrite destination `returnCell`, coordinates, or expedition IDs.
5. Keep the public gate methods and their idempotency semantics stable: `CanOpen`, `BeginOpening`, `SpendOpeningTicks` plus its receipt lookup, `TrySpendEmergencyReturnReserve`, `CanRecover`, `BeginRecoveryOpening`, and `CloseOpening`. Preserve operator assignment/station readiness, warnings, active/latest-closed IDs, emergency timing, and the existing time-cost/recovery receipt lists. The expedition component remains owner of crew transfer, map/site records, run status, and closure history.
6. Use the Battery's actual `StoredEnergy` as the physical store and its stable Thing reference as the binding. `AddEnergy` must not be called each tick for a battery still connected to a `PowerNet`: native network surplus already charges it. A reference to a battery on the settlement's shared network does not reserve its charge; other consumers can drain it. For a dedicated emergency reserve, require the designated battery/network to be gate-only (or label the reserve non-exclusive and do not guarantee emergency power). Only call `DrawPower` after checking actual stored energy, and only for one accepted operation/energy debit.
7. Remove the current strategy of writing `PowerOutput` on the threshold's native `CompPowerTrader`. On Autodoor that trader belongs to Core door operation and has a Def-defined 50 W baseline; Rimrooms replacing it with 250/3,500 W is a competing use of the same native consumer and `SetUpPowerVars()` restores Def values on power setup. Pick one visible portal-energy accounting path: use native network load for a designated Rimrooms power consumer, or debit the linked gate-only Battery for a separately stated portal cost. Do not charge the same watt cost through both paths or keep a second float capacitor alongside the real Battery. `CurrentEnergyGainRate`/`CanPowerNow` are aggregate/current estimates, never individual delivery evidence.

The current native door itself only opens for pawn passage. Its `Open` flag does not establish a Rimrooms expedition. If the portal must visibly remain open for the saved window, that requires a separate reviewed presentation/control route; do not mutate private door fields or call the protected `DoorOpen(int)` through reflection. The existing expedition service transfers pawns between maps after staging near the gate; preserve that service rather than treating ordinary local door pathing as cross-map travel.

`CompRimroomsGate` currently serializes `rr_gateAssignedOperator`, `rr_gateAssemblyComplete`, `rr_gateCalibrated`, `rr_gateActiveExpeditionId`, `rr_gateOpeningTicksRemaining`, `rr_gateEmergencyReturnTicksRemaining`, `rr_gateEmergencyReturnSpent`, three `rr_gateWarned*Window` flags, `rr_gateFailureKey`, `rr_gateReturnReserveStored`, `rr_gateStablePowerTicks`, `rr_gateLastClosedExpeditionId`, `rr_gateOpeningSpendReceipts`, and `rr_gateRecoveryReceipts`. `CompRimroomsGateConsole` saves `rr_gateConsoleLinkedGate` and `rr_gateAssemblyBillCreated`; calibration work saves `rr_gateCalibrationWorkDone`. Keep these old keys and meanings intact; append provider/link/binding fields under new keys. Existing native Battery energy is already saved by Core under `storedPower` and must remain owned by that exact Battery object.

**Legacy boundary:** retain `RR_MachineGate`, `RR_GateConsole`, cutoff, and generator Def identities as hidden migration-only Defs while supported development saves may contain them, or publish an explicit fresh-save/development-save break and preserve the matching old package. Do not remove a Def referenced by a saved `Thing`. Mark old gates legacy; do not auto-create native doors/consoles/batteries, rerun assembly bills, set calibration/assembly complete, copy `rr_gateReturnReserveStored` into a Core Battery, refill a reserve, replay a `Begin*` receipt, or pay/grant anything during load. Preserve original `rr_gate` references and operation IDs. New dispatch must select only a player-bound native gate; existing run handling must remain tied to its recorded legacy gate until it is explicitly closed/recovered or the owner declares the save boundary. The old numeric reserve is historical legacy state, not proof of energy stored in a newly selected Battery.

## Handoff and remaining proof

This map identifies the implementation scopes; it does not establish a native gate integration or save migration. The owning implementation change should update the gate component/API, console/assembly link, power/battery accounting, native selection, scenario/facility/failure-content references, and source records as one bounded change. The integrated build and owner-launched disposable-save cases must separately verify old active/stranded runs, dispatch/return/recall/recovery/abandon, duplicate operation receipts, missing/reassigned door-console-battery links, power outages/EMP/breakdown/brownout, ordinary native CommsConsole interaction, actual Battery behavior on a shared versus dedicated net, entry-cell reachability in each door orientation, and save/reload without replayed grants. No such test was run for this note.
