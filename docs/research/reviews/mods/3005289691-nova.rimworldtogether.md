## What the sources say

- The Workshop page describes separate colonies on one shared planet, with visits, raids, trading, faction creation, roads, and sites.
- The official wiki describes sending events, trading items and pawns, and modifying shared world features. Its configuration guide identifies offline visits and raids as configurable activities, with separate controls for sites, roads, aid, and trade. The trading guide says direct trades and gifts require both players online; mod-specific items may fail to transfer.
- The wiki says direct real-time play on shared world tiles is planned for the future. This fits Rimrooms' intended asynchronous company visits better than live shared-map control, but a listed feature is not proof that a particular visit behaves as a safe, read-only facility tour.
- Release `26.8.31.1` adds world-river synchronization and Odyssey asteroid compatibility. It is the latest upstream release found in this review; the local server archive digest matches its published Windows asset.
- The local server uses `Configs\Actions\*.json`, not the flat `ActionConfigs.json` named in the wiki. `Aid.json` and `Trade.json` are enabled with cooldown 250; `Caravan.json` and `Raid.json` are also enabled. There is no local Visit or Activity action file, and `ServerConfig.json` has no `EnableActivities` field, so offline visits are not established from this snapshot. `ScenarioConfig.json` enforces `Crashlanded`; test alternate starts only with a disposable configuration copy. See the [audit](../../RWT_AND_GRAVSHIP_FEASIBILITY.md) for hashes and full paths.
- The reviewed public repository presents a server source project and distributed client assemblies. A supported client extension contract for Rimrooms has not been established; do not design against assumed RWT internals.

## Rimrooms design translation

Treat RWT as the **company-to-company layer**: each player runs a separate facility and keeps their own staff, gate, discoveries, contracts, and finances. If enabled and verified, players can visit while the other branch is offline. Direct trades and gifts require both players online according to the official guide, so do not describe them as unattended shipments. Test aid and each transfer route independently. Their shared story can emerge from handoffs, radio reports, missing-person cases, recovered objects, and visits to a colleague's facility.

Keep live co-control of one facility out of the design. Do not promise shared research, custom dossiers, or transfer of Rimrooms-only items until the exact two-client setup proves them safe. The first useful test is modest: two separate facilities, an offline visit, an ordinary cargo transfer, aid, reconnect, and a check that neither branch loses or duplicates anything.

## Remaining evidence

- Confirm offline-visit availability and scenario controls using a disposable server copy; the current local server enforces Crashlanded and its config does not expose a visit/activity switch.
- Test ordinary direct trades/gifts with both players online, test aid separately, then test offline visit and reconnect behavior. The official guide also documents vanilla drop-pod transfer but does not state whether an offline target receives it; verify this candidate before promising async cargo.
- Check whether different starts can join one server and keep separate opening states without changing the actual server installation.
- Test ordinary goods first, then custom dossier/cargo only after implementation exists; record receipts, reconnect behavior, saves, and errors. Upstream [issue #296](https://github.com/RimWorld-Together/Rimworld-Together/issues/296) reports pawn-state problems after aid; inspect identity, faction, health, equipment, destination, and post-reconnect state.
- Inspect client extension options only if a proposed Rimrooms feature genuinely needs them.
