## What the sources say

- The Workshop page describes separate colonies on one shared planet, with visits, raids, trading, faction creation, roads, and sites.
- The official wiki describes sending events, trading items and pawns, and modifying shared world features. Its configuration guide identifies offline visits and raids as an available activity, with separate switches for sites, roads, aid, and trade.
- The wiki says direct real-time play on shared world tiles is planned for the future. This fits Rimrooms' intended asynchronous company visits better than live shared-map control, but a listed feature is not proof that a particular visit behaves as a safe, read-only facility tour.
- Release `26.8.31.1` adds world-river synchronization and Odyssey asteroid compatibility. It is the latest upstream release found in this review; the local server archive digest matches its published Windows asset.
- Local server configuration files do not include an `ActionConfigs.json`, so the active visit, aid, and trade switches have not been established from this installation.
- The reviewed public repository presents a server source project and distributed client assemblies. A supported client extension contract for Rimrooms has not been established; do not design against assumed RWT internals.

## Rimrooms design translation

Treat RWT as the **company-to-company layer**: each player runs a separate facility and keeps their own staff, gate, discoveries, contracts, and finances. If the pinned build supports it, players can visit while the host is offline, exchange supported supplies, and send aid. Their shared story can emerge from handoffs, radio reports, missing-person cases, recovered objects, and visits to a colleague's facility.

Keep live co-control of one facility out of the design. Do not promise shared research, custom dossiers, or transfer of Rimrooms-only items until the exact two-client setup proves them safe. The first useful test is modest: two separate facilities, an offline visit, an ordinary cargo transfer, aid, reconnect, and a check that neither branch loses or duplicates anything.

## Remaining evidence

- Confirm which offline visit, aid, and item-transfer options are enabled on the pinned server, using a disposable world.
- Check whether different Rimrooms starts can join one server and keep separate opening states.
- Test ordinary goods first, then custom dossier/cargo only after implementation exists; record receipts, reconnect behavior, saves, and errors.
- Inspect client extension options only if a proposed Rimrooms feature genuinely needs them.
